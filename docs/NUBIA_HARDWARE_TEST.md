# Lastphone alpha: аппаратный тест Nubia Z60 Ultra

Сценарий подготовлен для **NX721J / cerro**, ARM64, Android 10/API 29 или новее.
Подготовка пакета и успешная сборка не означают, что телефон прошёл тест.
Результат появляется только после запуска на физическом устройстве.

## Что именно проверяем

Опубликованная [alpha 1](https://github.com/qqrm/lastphone/releases/tag/v0.1.0-alpha.1)
собрана из `bc18a4d0322056ee040ad3d0524460ca309117db`.
SHA-256 APK: `e7371806d010ebaf3914cb5054c0f78b7fb4e1dabc929c59769adacdfba975fc`.
Её [18 тестов на эмуляторе](ANDROID_VALIDATION.md) подтвердили Android-интеграцию
и CPU. Vulkan-ветка на эмуляторе проверила отказ недоступного GPU, без вычислений
на Adreno.

Аппаратный пакет содержит отдельную сборку **Lastphone HW test**:

| Назначение | Application ID |
| --- | --- |
| Опубликованная alpha | `io.github.qqrm.lastphone` |
| Изолированное тестовое приложение | `io.github.qqrm.lastphone.hardwaretest` |
| Инструментальные тесты | `io.github.qqrm.lastphone.hardwaretest.test` |

Тестовая сборка использует тот же прикладной код, но имеет другой ID и отдельную
подпись/сборку. Её SHA и SHA обоих APK записаны в `hardware-test-bundle.json`.
Успех тестовой сборки **не является проверкой байтов опубликованного APK**:
ручной проход опубликованной alpha отмечается отдельно в отчёте.

Автоматизация устанавливает только изолированную пару APK. Основная установка,
её настройки и библиотека не очищаются. Не открывайте единственный экземпляр
рабочей библиотеки в тестовом приложении: для ручного прохода используйте копию.
При несовпадении подписи уже установленной тестовой сборки запуск останавливается;
автоматического удаления приложения нет.

## 1. Подключение и проверка готовности

На Windows нужны **Python 3.10+** и
[Android SDK Platform Tools](https://developer.android.com/tools/releases/platform-tools).
Команды `python` и `adb` должны быть доступны в терминале. Если Python доступен
через Windows launcher, замените `python` на `py -3`. PowerShell-обёртка
`run_hardware_tests.ps1` сама выбирает установленный Python и принимает те же аргументы.

1. Распакуйте аппаратный пакет в отдельную папку.
2. Включите USB debugging на Nubia, подключите USB и подтвердите ключ компьютера
   на разблокированном экране. Запускайте тест в основном пользователе Android
   (user 0), а не во вторичном пользователе или рабочем профиле.
3. Выполните `adb devices -l`, скопируйте серийный номер строки со статусом `device`.
   `unauthorized` и `offline` не подходят. Эмулятор и другая модель не принимаются.
4. В терминале из папки пакета выполните:

```powershell
python .\run_hardware_tests.py preflight --serial SERIAL --output .\results-preflight
```

Вместо `SERIAL` подставьте номер Nubia. Для ADB вне `PATH` добавьте
`--adb C:\Android\platform-tools\adb.exe`. В Linux используйте `python3` и `/`.
В исходном репозитории путь к скрипту — `tools/android/run_hardware_tests.py`.

Preflight сохраняет модель, прошивку, ABI, RAM, размер страницы памяти и доступные
системные сведения. Номер модели не определяет объём RAM и версию GPU-драйвера —
в отчёт входят фактические значения устройства.

## 2. Smoke: обязательный первый прогон

На телефоне сначала вручную выключите **Wi-Fi** и **мобильные данные**, затем
включите **режим полёта**. Оставьте экран разблокированным. Автоматизация проверяет
эти условия и не меняет их сама. После завершения верните связь вручную.

```powershell
python .\run_hardware_tests.py smoke --serial SERIAL --manifest .\hardware-test-bundle.json --output .\results-smoke
```

Проверяются контрольные суммы APK, затем запускаются исходные **18 тестов** и
`HardwareAcceptanceTest#hardwareSmoke`. Аппаратная проверка требует настоящего
Vulkan-устройства, загрузки модели с GPU-offload и успешной генерации. Отсутствие
Vulkan не превращается в успешный CPU fallback. CPU, отмена и следующая генерация
проверяются отдельно. Маленькая модель входит только в тестовый APK.

Ожидаемый результат — **19 завершённых тестов**, без ошибок и пропусков, плюс
свежее аппаратное свидетельство. Нулевой exit code самого ADB не считается успехом.
Тайм-аут, потеря устройства, crash, пропущенный тест или отсутствие результата
оставляют неуспешный отчёт с доступными логами.

## 3. Реальная модель: CPU, Vulkan и длительная нагрузка

Подготовьте локальный GGUF, которым собираетесь пользоваться. Скрипт не скачивает
модель, считает SHA-256 и копирует её в приватный каталог тестового приложения.
Нужно свободное место для этой дополнительной копии. Файл исходной модели остаётся
на компьютере; модель в основной установке Lastphone не используется.

Первый функциональный прогон — по пять минут на backend:

```powershell
python .\run_hardware_tests.py benchmark --serial SERIAL --manifest .\hardware-test-bundle.json --model C:\Models\model.gguf --context 2048 --threads 4 --tokens 128 --duration-seconds 300 --repeats 3 --output .\results-model
```

После него проведите длительный прогон: замените `--duration-seconds 300` на
`--duration-seconds 900`. Это **15 минут на каждый backend**, плюс загрузки и
завершение текущей генерации. Параметр `--repeats` задаёт число начальных измеряемых
генераций перед длительной фазой. Для `--context` используйте кратное 256 значение
от 256 до 32768: нативный runtime округляет контекст до этого блока. Затем дайте
телефону остыть до сопоставимого состояния и повторите с `--backend-order vulkan,cpu` и новым
каталогом результата. Так эффект второго, уже нагретого прогона не выдаётся за
разницу CPU/GPU.

Для увеличенного числа повторений можно явно задать общий предел
`--timeout-seconds` (60–7200 секунд). По умолчанию smoke ограничен 1200 секундами,
benchmark — большим из 1200 и `2 × duration + 900`. Отдельная нативная загрузка
запрашивает отмену после 300 секунд, генерация — после 180; общий предел завершает
также зависший процесс тестового приложения.

Зафиксируйте режим питания, яркость, чехол, комнатную температуру и зарядку.
Не отключайте системное тепловое управление. При системном предупреждении о
перегреве остановите нагрузку; прерванный прогон не считается завершённым.

### Как читать измерения

- `first_text_ms` — время до первого видимого фрагмента текста. Callback может
  объединять байты нескольких токенов; это не точная граница первого токена.
- `n_gen`, `gen_ms`, `prompt_ms`, `n_prompt`, `n_reused` приходят из нативного
  раннера. Скорость нового prefill считают по `n_prompt - n_reused`; генерацию —
  по `n_gen`. При нулевой длительности в миллисекундах скорость не вычисляют.
- «Холодная» загрузка означает, что модель выгружена из приложения. Кеш страниц
  ОС не сбрасывается; копирование и хеширование уже могли его прогреть. Это не
  измерение чтения с холодного накопителя.
- Для Vulkan `n_gpu_layers=-1` означает выбор всех слоёв. Сведения `fit` и
  `device_bytes` — оценка памяти до загрузки, а не измерение занятой GPU-памяти.
  Наличие backend проверяется вместе с offload и успешной генерацией.
- Сравнивайте одинаковые SHA модели, контекст, prompt, потоки и backend-порядок.
  Фиксируйте фактический контекст из результата загрузки. Побайтовое совпадение
  ответов CPU и Vulkan не является критерием.
- Сохраняйте весь ряд скорости, памяти и thermal status. Нулевой thermal status
  сам по себе не доказывает отсутствие throttling: поддержка API зависит от
  прошивки. Недоступные датчики отмечаются как недоступные, не как нулевой нагрев.
- Benchmark держит частичную wake lock, чтобы измерение не останавливалось при
  выключении экрана. Он не подтверждает поведение обычного приложения в фоне;
  для этого есть отдельный ручной сценарий.

Порог tok/s заранее не задан: сначала получаем честную базовую линию. Замедление
под нагревом измеряется, а crash/ANR, потеря данных, зависшая отмена и скрытый
переход Vulkan на CPU считаются дефектами.

## 4. Ручной проход с реальной библиотекой

После автотестов откройте **Lastphone HW test** и выберите копию реального набора
через Settings → Open a library folder. Тесты оставляют выбранной синтетическую
библиотеку. Каждую строку отмечайте в
[шаблоне отчёта](NUBIA_HARDWARE_REPORT_TEMPLATE.md) вместе с названием пакета/файла.
Без нужного содержимого строка получает `BLOCKED`, а не `PASS`.

| Сценарий | Действия и ожидаемое свидетельство |
| --- | --- |
| Offline cold start | При выключенной связи закройте приложение, запустите заново. Каталог, поиск и уже загруженные материалы доступны без сети. |
| PDF, HTML, ZIM | Откройте реальные документы, несколько страниц и результатов поиска, проверьте кириллицу, ссылки и возврат назад. Запишите конкретные файлы. |
| Видео и субтитры | Полноценное воспроизведение со звуком, перемотка вперёд/назад, переход по времени из расшифровки. Проверяйте реальные кодеки пакета. |
| Карты и 3D | Область, реально присутствующая в пакете: масштабирование, перемещение, доступные слои и здания. Отсутствующий регион не считается ошибкой renderer. |
| Переносимая папка и SAF | Проверьте оба сценария: открытие папки на месте и импорт отдельной копии. После повторного запуска доступ и выбранная папка сохраняются; оригинал не изменён. |
| История и закладки | Создайте записи, перезапустите приложение и проверьте сохранность. Повторите после ручного force-stop и перезагрузки телефона. |
| UI и жизненный цикл | Поворот экрана, Home → возврат, блокировка на минуту → возврат во время чтения и генерации. Зафиксируйте, продолжилась или корректно остановилась работа, нет ли зависания/потери данных. |
| Отмена модели | Нажмите Stop во время длинного prefill и генерации; затем задайте новый вопрос. Автоматическая отмена после первого callback не заменяет эту проверку UI. |
| Реальный контекст и память | Повторите рабочий запрос с нужной длиной контекста, затем с более тяжёлой конфигурацией. Контролируемое сообщение «не помещается» допустимо для отрицательной проверки; оно не подтверждает пригодность исходно требуемой конфигурации. Не заполняйте накопитель до отказа. |
| LAN, отдельная online-фаза | После offline-прохода включите локальную сеть, явно запустите sharing, откройте выданную ссылку на втором устройстве, затем остановите sharing. Нет второго устройства — `BLOCKED`. |

Force-stop и перезагрузка прекращают процесс; возобновление прежней генерации
автоматически не требуется. Проверяется чистый запуск и сохранность данных.
Ручные действия выполняются в тестовой установке; автоматический сценарий не
перезагружает телефон и не закрывает другие приложения.

Для вывода именно об опубликованной alpha повторите основные UI/offline/lifecycle
сценарии в `io.github.qqrm.lastphone`, установив APK с указанным выше SHA.
Не заменяйте существующую установку при конфликте подписи и не удаляйте её ради
теста. В отчёте явно различайте результат тестовой сборки и опубликованного APK.

## 5. Батарея и размер страницы памяти

USB-прогон может заряжать телефон. Его battery telemetry пригодна как контекст
нагрузки, но не даёт корректного расхода батареи. Для отдельного замера отключите
кабель, оставьте одинаковыми яркость/связь/модель/контекст и выполните одинаковый
30-минутный сценарий через UI. Запишите начальный/конечный заряд, время, режим
питания и температуру; сравните CPU и Vulkan из сопоставимого состояния. Падение
заряда в процентах — грубая оценка, не измерение энергии в ватт-часах. Отсоединять
USB во время автоматического прогона не нужно: это прервёт его управление.

`PAGE_SIZE=4096` подтверждает только запуск на 4 KiB. Проверка ELF-выравнивания
16 KiB в сборке и успешный тест такой Nubia **не подтверждают исполнение на
16 KiB**. Для последнего нужен отдельный ARM64 runtime с `PAGE_SIZE=16384`.
Прошивка телефона или изменение его режима памяти в этот сценарий не входят.

## Результат и передача отчёта

Каждый запуск сохраняет `summary.json`, `report.zip`, сведения устройства,
инструментальный вывод, логи, telemetry и доступные аппаратные свидетельства.
Для разбора достаточно соответствующего `report.zip` и заполненного ручного
отчёта. Не публикуйте автоматически архив с личным содержимым библиотеки или
идентификаторами устройства.

| Статус | Значение |
| --- | --- |
| `READY` | Preflight нашёл подходящую физическую Nubia. Тесты приложения ещё не выполнены. |
| `PASS_AUTOMATED` | Завершился выбранный автоматический этап; `hardware_acceptance` остаётся `pending_manual`. |
| `FAIL` | Тест выполнен с ошибкой, Vulkan не сработал, процесс упал/завис или результат недостоверен. |
| `BLOCKED` / `HARDWARE_UNAVAILABLE` | Нет подходящего подключённого телефона, разрешения ADB, артефакта, модели или нужного контента. Это не пройденный тест. |
| Частичная аппаратная проверка | Есть успешные этапы, но ручные сценарии, рабочая модель, батарея или опубликованный APK ещё не проверены. Перечислить оставшиеся пункты. |
| Аппаратная приёмка конкретной конфигурации | Smoke, нужная рабочая модель и применимые ручные сценарии пройдены; зафиксированы прошивка, APK, модель, контекст и ограничения. Не обобщать на другие модели/прошивки. |
